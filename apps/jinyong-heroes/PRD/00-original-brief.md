可行。真正困难的不是网页技术，而是两件事：

第一，把 1996 年 DOS 版的所有隐藏规则、事件条件、数值和历史 Bug 挖完整；第二，建立一套严格的验收体系，防止开发过程中“不知不觉做成现代武侠 RPG”。

我建议把项目正式定义为：

以 1996 年 DOS 版《金庸群侠传》为唯一基准，在浏览器中重新实现其全部剧情、地图、任务、人物、战斗、物品、武功、成长和正邪路线；现代化只发生在操作、分辨率、存档和兼容性层面，不改变游戏内容与数值。

原作是河洛工作室开发、智冠科技于 1996 年发行的 DOS 单机战棋 RPG；其核心目标是收集十四部天书、参加武林大会并最终返回现实世界。

## 一、先确定“极致复刻”的验收标准

复刻完成后，应满足以下四条硬标准：

1. **旧攻略完全有效**  
   玩家拿着当年的攻略，地图坐标、物品位置、队友加入条件、十四天书顺序都能正常使用。
2. **相同状态得到相同结果**  
   相同人物属性、武功等级、装备、位置和随机种子下，行动顺序、伤害、用毒、升级和 AI 行为与原作一致。
3. **全部内容可达**  
   十四天书、所有队友、全部正邪选择、全部秘笈装备、所有隐藏入口、武林大会及最终十大高手战都可正常完成。
4. **不偷偷现代化数值**  
   不增加装备品质、天赋树、随机词条、动态等级、任务导航、每日任务、抽卡、赛季或联网养成。

“网页游戏”只是运行方式，不是玩法改造。

## 二、版权边界必须提前处理

技术上可以做到一比一，但公开发布与内部复刻是两件事。

中国著作权法明确保护文字、美术、音乐、视听作品和计算机软件，改编权、复制权、信息网络传播权也属于权利人的专有权利。司法实践中，游戏的人物、场景、技能、装备、地图和组合关系高度近似，也可能被认定为侵犯改编权或信息网络传播权。玩法规则和抽象系统相对可以借鉴，但金庸人物、原作故事、原游戏台词、美术、音乐不能当然地自由复制。

因此技术方案可以分成三种发布形态：

- **私人或内部研究版**：完整复刻，限定访问，不公开传播。
- **原版文件导入版**：网页引擎本身不携带素材，用户在本地导入自己拥有的原游戏文件，由浏览器转换并加载。这样可以减少直接分发原素材的问题，但不代表自动解决所有版权风险。
- **正式公开版**：取得小说和原游戏相关授权后完整发布。

下面的方案按照“技术上一比一复刻”设计。

## 三、产品形态：原典模式和增强模式共用一套逻辑

不要维护两个游戏，只维护同一套核心数据和规则，提供两个表现模式。

### 原典模式

- 原版地图、碰撞、人物位置和事件范围。
- 原版数值、AI、随机数和行动逻辑。
- 不显示资质、成长参数、事件 Flag 等隐藏数据。
- 无任务箭头、无地图路径、无敌人等级提示。
- 原版速度和战斗节奏。
- 保留不影响通关的历史特性和怪异逻辑。
- 原版像素风格、最近邻缩放、固定逻辑画面。

### 增强模式

- 剧情、任务、数值和战斗完全不变。
- 高清字体、触屏操作、键鼠操作。
- 1倍、2倍、4倍战斗速度。
- 自动存档、更多存档槽、存档导出。
- 已发现地点列表，但不直接揭示未发现地点。
- 可查看物品说明和武功修炼要求。
- 可选任务笔记，只记录玩家已经获知的信息。
- 崩溃、坏档、卡死类 Bug 修复。

最重要的原则是：

增强模式只能减少操作摩擦，不能降低探索和决策难度。

### 任务引擎必须是数据驱动的

不能把剧情散落在 React 组件或地图代码中。每个事件都应表达为：

```yaml
id: rumor_meizhuang
scene: yuelai_inn
trigger:
  type: talk
  actor: waiter
conditions:
  all:
    - flag_not_set: meizhuang_known
actions:
  - dialogue: dialogue_rumor_meizhuang
  - set_flag: meizhuang_known
  - unlock_location: meizhuang
```

完整事件模型至少包含：

```ts
type EventDefinition = {
  id: string;
  sceneId: string;
  trigger:
    | "ENTER"
    | "TALK"
    | "INTERACT"
    | "USE_ITEM"
    | "BATTLE_WIN"
    | "BATTLE_LOSE"
    | "PARTY_CHANGE";
  conditions: ConditionTree;
  actions: EventAction[];
  priority: number;
  repeatable: boolean;
};
```

条件系统必须支持：

- 是否拥有某物品。
- 某物品数量。
- 某人物是否在队。
- 队伍是否已满。
- 道德和声望范围。
- 是否已经见过某人。
- 某 NPC 是否存活、离开或加入。
- 某战斗是否完成。
- 某地图入口是否已获知。
- 已获得天书数量。
- 多条件的 all / any / not 嵌套。

行为系统必须支持：

- 播放对话。
- 设置或清除 Flag。
- 添加或移除物品。
- 增减道德、声望。
- 开启地点。
- 改变地图物件。
- NPC 加入、离开、死亡、移动。
- 主角或队友单挑。
- 启动团队战。
- 传送玩家。
- 改变结局路线。

整个游戏的本质就是：

玩家行为 → 检查世界状态 → 命中事件条件 → 执行事件动作 → 产生新的世界状态

## 五、人物系统：隐藏属性必须保留

人物不是简单的“等级+装备”。

原作可见属性包括等级、生命、内力、体力、攻击、防御、轻功、医疗、用毒、解毒以及拳、剑、刀、暗器等熟练度；等级上限为30，基础攻击、防御、轻功等主要能力上限为100，生命和内力上限为999。内力还区分阴、阳和阴阳调和。战斗经验会同时进入人物升级和当前修炼秘笈。

人物数据建议完整保存：

```ts
  level: number;
  maxHp: number;
  maxMp: number;
  stamina: number;
  attack: number;

  dismissalRule: ConditionTree;

```

必须完整复刻的角色特性包括：

- 段誉进入燕子坞后自动离队，直到天龙八部相关剧情结束。
- 胡斐需要两页刀法才加入。
- 程灵素需要胡斐在队。
- 杨过需要解除情花毒。
- 虚竹、程瑛、狄云等受道德限制。
- 阿紫、游坦之偏向低道德路线。
- 欧阳克要求队伍中有女性。
- 令狐冲的加入涉及烧刀子、梅庄、梨花酒、翡翠杯和思过崖。
- 王语嫣不是普通输出角色，她的“武学知识”会影响全队实际战斗计算。

这些条件不能简化成“完成角色支线即可加入”，否则原作的队伍规划价值会消失。原版资料对主要队友加入条件有明确记录。

队伍人数、离队后的去向、是否可以再次招募，也必须由原版行为决定，不能统一处理。

## 六、武功和成长：不要重新设计，只做精确实现

原版武功系统应保留：

- 每个角色最多学习固定数量武功。
- 武功最高十级。
- 武功通过战斗使用和修炼秘笈成长。
- 资质决定修炼速度。
- 某些武功要求阴性、阳性或调和内力。
- 某些武功限定人物。
- 某些秘笈只增加属性，不产生主动招式。
- 武功范围随等级变化。
- 内力不足时，实际使用的武功等级会下降。
- 左右互搏产生双次攻击。
- 武器与指定武功存在绑定加成。
- 医书、毒经可以增加能力并炼制特定药物。

原版操作手册记录了大量秘笈要求和效果，例如易筋经、九阴真经、九阳真经、降龙十八掌、玄铁剑法、辟邪剑谱、左右互搏，以及武器和防具的属性变化。

不要把武功改成现代游戏常见的“主动技能+冷却时间”。原版的资源约束是内力、体力、距离、受伤和武功等级。

## 七、战斗系统：必须实现“原版数学”，不能凭感觉调数值

这是复刻最容易失真的地方。

社区的 DOS 重实现项目已经整理出一份相当细的战斗数学规格，其中包括原版随机数生成方式、16位整数行为、行动顺序、移动步数、伤害、距离衰减、受伤、中毒、熟练度、升级和 AI 决策。它可以作为重要参考，但仍应通过原游戏实测进行二次校验。

### 1. 确定性随机数

原版使用共享的线性同余随机序列。随机数调用的次数和顺序也会影响后续结果。

因此不能直接使用：

```ts
Math.random()
```

而应实现专门的原版 RNG：

```ts
class ClassicRng {
  private seed: number;
  next(): number {
    this.seed =
      (Math.imul(this.seed, 0x41c64e6d) + 0x3039) >>> 0;
    return (this.seed >>> 16) & 0x7fff;
  }
  bounded(n: number): number {
    if (n <= 1 || n > 30000) return 0;
    return this.next() % n;
  }
}
```

此外要实现：

- 16位有符号整数回绕。
- 整数除法向零取整。
- 原版随机调用顺序。
- 战斗开始时保存随机种子。
- 通过“种子+操作序列”重放整个战斗。

这样战斗 Bug 才可复现，自动测试也才可靠。

### 2. 行动和移动

原版行动顺序主要根据：

轻功/速度 + 武器速度 + 防具速度

移动步数受速度和受伤程度影响。受伤越重，不仅移动距离下降，攻击和防御效果也会受影响。

应严格复刻：

- 等速角色的原始排序行为。
- 移动格洪泛算法。
- 地形和建筑阻挡。
- 人物占位对移动的影响。
- 攻击射程与移动寻路使用不同距离图。
- 等待后移动到本轮队尾。

### 3. 攻击范围

原版主要存在四类范围：

- 单体。
- 直线。
- 十字。
- 以目标格为中心的区域。

独孤九剑、九阳神功、太玄神功、霹雳刀法等大范围武功的手感，主要来自范围、射程、内力消耗和伤害衰减的组合，不能只复制技能名称。

### 4. 伤害和状态

实际攻击应综合：

人物攻击 + 武功当前等级威力 + 武器和防具攻击增量 + 武器绑定加成 + 武学知识影响

实际伤害再综合：

实际攻击 - 实际防御 + 随机波动 + 施术者体力 + 目标受伤程度 - 距离衰减

还要同时处理：

- 目标受伤值。
- 中毒值。
- 抗毒。
- 回合末受伤和中毒结算。
- 击杀经验。
- 区域武功只扣一次内力。
- 吸星大法、北冥神功等吸取内力逻辑。
- 左右互搏第二击沿用目标。
- 武功熟练度每次攻击后的增长。

### 5. AI

敌人 AI 不需要“变聪明”，必须先和原版一样。

其决策顺序大致是：

体力不足 → 是否需要补血 → 是否需要解毒 → 是否需要补内力 → 是否可以医疗队友 → 是否用毒或暗器 → 选择武功和目标 → 选择站位 → 无法行动则休息

智能化 AI 可以作为独立的“挑战模式”，绝不能覆盖原典模式。

## 八、物品系统：剧情道具和普通道具必须共用统一模型

原版物品不是简单背包列表，至少包括：

- 天书。
- 剧情信物。
- 钥匙和地图。
- 武功秘笈。
- 医书和毒经。
- 武器。
- 护具。
- 药品。
- 解毒物。
- 永久属性药物。
- 暗器。
- 炼药材料。
- 银两。

物品定义：

```ts
type ItemDefinition = {
  id: string;
  name: string;
  category: ItemCategory;
  stackable: boolean;
  equipRequirements?: ConditionTree;
  trainingRequirements?: ConditionTree;
  statModifiers?: Partial<CharacterStats>;
  consumeEffects?: Effect[];
  recipe?: {
    materialId: ItemId;
    materialCount: number;
    outputId: ItemId;
  };
  questTags?: string[];
  boundSkillId?: SkillId;

```

特别需要保留：

- 秘笈的修炼门槛。
- 武器的武力、内力和兵器熟练度要求。
- 装备可能同时增加攻击、防御或轻功，也可能降低轻功。
- 医书和毒经修炼过程中产出药品。
- 暗器数量消耗。
- 特殊药品永久提升属性。
- 宝箱和屋内物品的所有权。

原作还有一个很重要的道德规则：翻别人箱子可能降低道德，但主人已经离开、允许搜取或已经加入队伍时不扣。这意味着地图物件必须拥有“所有者”和“盗取判定”，不能只做普通宝箱。

## 九、地图系统：完整复刻三层地图

地图分成三类。

### 1. 世界大地图

- 保留原版地点坐标和相对位置。
- 海岛、河流、山脉、船只通行规则一致。
- 未获知地点不能直接传送。
- 地图地点是否可进入，由世界 Flag 控制。
- 罗盘显示坐标。
- 增强模式可显示已发现地点名称，但不提前揭示隐藏地点。

原版攻略保存了白驼山、百花谷、冰火岛、燕子坞、黑木崖、光明顶、桃花岛等大量地点坐标，可直接形成地图验收表。

### 2. 场景地图

每张场景包含：

地面层、碰撞层、遮挡层、NPC层、可交互物层、事件区域层、传送点层、音效区域层。

每个箱子、书架、床、墓碑、花草、墙壁机关都必须是独立交互对象。

### 3. 战斗地图

- 使用独立网格和初始站位。
- 完整保留敌我名单和敌人携带物。
- 保留人物占位、障碍和射程。
- 战前选人和布阵逻辑保持原版。
- 某些单挑强制指定角色出战。

## 十、网页端技术架构

我不建议直接用 React 编写游戏逻辑，也不建议把 Unity WebGL 当第一选择。最适合的是“纯 TypeScript 核心 + 2D 游戏渲染层”。

推荐的工程结构：

```text
jy-web/
├── apps/
│   ├── game-client/       # 网页游戏
│   ├── content-editor/    # 剧情和数据编辑器
│   └── debug-console/     # 状态检查与事件调试
│
├── packages/
│   ├── game-core/         # 纯逻辑，不依赖浏览器
│   ├── battle-core/       # 战斗和原版整数/RNG
│   ├── event-engine/      # 任务事件解释器
│   ├── content-schema/    # 数据结构和校验
│   ├── renderer/          # Phaser/Pixi 渲染
│   ├── save-system/       # 存档和版本迁移
│   └── original-importer/ # 原始资源导入工具
│
├── content/
│   ├── characters/
│   ├── skills/
│   ├── items/
│   ├── scenes/
│   ├── battles/
│   ├── events/
│   └── dialogues/
│
└── tests/
    ├── battle-golden/
    ├── quest-paths/
    ├── save-compat/
    └── original-parity/
```

（本仓中该项目位于 `apps/jinyong-heroes/`，后续拆包时再落到上述结构。）

### 核心原则

`game-core` 必须完全脱离画面层。

```ts
const result = gameCore.dispatch({
  type: "INTERACT",
  actorId: "player",
  targetId: "chest_iron_palm_03"
});
```

核心返回：

```ts
{
  stateChanges: [...],
  dialogueEvents: [...],
  audioEvents: [...],
  animationEvents: [...]
}
```

渲染层只负责把结果表现出来，不能直接修改道德、背包或剧情 Flag。

这样才能：

- 自动测试全部剧情。
- 在 Node.js 中模拟完整通关。
- 更换画面而不改变逻辑。
- 生成战斗回放。
- 对比原版行为。
- 将来制作原创武侠版本。

### 客户端

建议：

- TypeScript。
- Phaser 或 PixiJS 负责 Tilemap、Sprite、动画和输入。
- React 仅负责启动页、设置、存档和编辑器。
- IndexedDB 保存本地存档。
- Service Worker 提供离线 PWA。
- WebAudio 管理音乐和音效。
- 固定逻辑分辨率，按整数倍或最近邻方式缩放。
- PC 支持键盘、鼠标。
- 手机默认横屏，支持点击移动和虚拟方向键。

单机游戏本身不需要后端。后端只用于可选的账号和云存档。

## 十一、内容生产方式：不要靠程序员手工写完全部任务

整个项目最重要的内部产品其实是编辑器。

编辑器至少需要：

- 世界地图地点编辑。
- 场景 Tilemap 编辑。
- NPC 和物件放置。
- 对话树编辑。
- 事件条件与动作编辑。
- 战斗人员和初始站位编辑。
- 人物、武功、物品表格编辑。
- 道德和声望变化审计。
- “为什么当前事件没有触发”的调试解释。
- 任意传送、添加物品、修改 Flag。
- 从任意任务节点开始测试。

调试器应能显示：

```text
梅庄入口：未开启
未满足条件：
✓ 已经与悦来客栈店小二交谈
✗ meizhuang_known = false
✓ 队伍状态合法
✓ 当前事件未完成
```

这种工具会显著减少“攻略明明正确，但门不开”的复刻事故。

## 十二、测试方法：把原版当作行为预言机

极致复刻不能只靠人工玩。

### 1. 战斗黄金样本

选择一批固定战斗：

- 初期门派守门人。
- 胡斐单挑苗人凤。
- 乔峰。
- 光明顶六大派。
- 梅庄四友。
- 东方不败。
- 侠客岛。
- 武林大会。
- 最终十大高手。

每场保存：

初始属性、装备、武功等级、初始位置、随机种子、每一步操作、每次伤害、每次状态变化、最终经验。

网页实现必须逐步一致。

### 2. 剧情路径测试

每本天书至少建立：

- 最短合法路线。
- 常规路线。
- 缺少关键队友路线。
- 队伍已满路线。
- 道德不足路线。
- 物品提前取得路线。
- NPC 已离队路线。
- 重复交谈路线。

### 3. 世界状态穷举

对核心任务图做自动检查：

- 是否存在永远无法满足的条件。
- 是否存在互相矛盾的 Flag。
- 是否存在拿走关键物品后无法继续。
- 是否存在 NPC 离队后主线永久中断。
- 十四本书是否全部至少有一条可达路径。
- 正邪结局是否都可达。

### 4. 旧攻略回归测试

把当年的攻略步骤直接转成自动脚本：

```ts
goTo("nanxian_house");
talkTo("nanxian");
receive("compass");
goTo("jiangnan_cave");
take("tang_poetry");
goTo("beichou_house");
useOn("tang_poetry", "water");
```

每次修改代码后自动执行完整攻略。

## 十三、Bug 兼容策略

应建立一张明确的 Bug 兼容表，不能随意决定。

### 必须保留

- 原版整数运算。
- 原版随机数和调用顺序。
- 原版武功成长曲线。
- 原版隐藏属性。
- 原版事件先后依赖。
- 原版奇怪但可玩的角色和物品行为。
- 原版正邪路线难度差异。

### 原典模式可保留、增强模式可修复

- 物品说明缺失。
- 存档槽过少。
- 战斗速度慢。
- 隐藏入口缺少反馈。
- 操作容易误点。
- 任务信息完全无法回顾。

### 两种模式都应修复

- 游戏崩溃。
- 存档损坏。
- 浏览器卡死。
- 必然导致无法通关的程序错误。
- 原版因内存或平台限制产生的技术问题。

修复后要记录：

```text
BUG-ORIGINAL-017
原版行为：带张无忌进入某事件可能异常
网页行为：事件正常执行
游戏数值和剧情结果：保持不变
```

## 十四、现有开源项目怎么利用

目前有两个很有价值的参考项目。

HeroesOfJinYong 是一个针对 DOS 原版的 C++ 重实现，包含原始资源转换工具以及战斗数学和 AI 文档，代码采用 GPLv3。适合用来研究数据格式、战斗公式和行为，但直接复制其代码前要评估 GPL 开源义务。

jynew/jynew 已经实现了脚本驱动剧情、数据编辑、地图、战斗和完整复刻流程，证明“完整数据化复刻”这条路线是可行的。但它基于 Unity，项目又明确限制其素材在项目之外使用，并强调非商业用途，因此不适合直接拿素材做独立网页产品。

我的建议是：

参考两个项目的行为和数据结构，但用 TypeScript 做一次 clean-room 网页实现。不要直接把 Unity 项目移植成 WebGL，也不要复制受限制的美术资源。

## 十五、具体实施顺序

### 阶段一：锁定原版基准

- 确定唯一参考版本。
- 保存原版文件哈希。
- 建立原版可运行环境。
- 收集操作手册、攻略、地图和数据表。
- 建立“原版事实库”。
- 对每个争议行为录屏和保存档。

不先锁版本，后面会不断争论“这到底是 Bug 还是版本差异”。

### 阶段二：完成无画面的核心引擎

先实现：

- WorldState。
- EventEngine。
- Character。
- Inventory。
- Skill。
- Battle。
- Save。
- ClassicRng。
- 原版整数运算。
- 剧情脚本解释器。

这一阶段甚至可以没有人物图片，只用文本和方格验证。

### 阶段三：用《连城诀》做第一个垂直切片

《连城诀》链路相对短，却包含：

- 世界移动。
- 场景探索。
- 拾取剧情物品。
- NPC 提示。
- 对物品进行特殊处理。
- 战斗。
- 隐藏位置取书。
- 天书状态更新。

第一个可玩闭环：

自宅 → 南贤 → 江南山洞 → 北丑 → 天宁寺 → 战斗 → 获得连城诀

这能验证80%以上的基础框架。

### 阶段四：用《笑傲江湖》做压力测试

《笑傲江湖》非常适合验证复杂任务能力：

- 多个前置道具。
- 多地点交叉。
- 连续单挑。
- 离开后重新进入。
- 地牢状态变化。
- 获得武功和令牌。
- 大型 Boss 战。
- 战后追加战斗。

原版攻略也把它视为较难取得的天书之一。

如果连城诀和笑傲江湖都能准确复刻，剩余十二条主线主要是内容录入和测试，而不是架构风险。

### 阶段五：补齐全部十四天书和队友

按任务之间的共用关系实施：

1. 飞狐外传、雪山飞狐。
2. 神雕侠侣、白马啸西风。
3. 天龙八部。
4. 射雕英雄传。
5. 倚天屠龙记。
6. 鹿鼎记。
7. 侠客行。
8. 书剑恩仇录。
9. 碧血剑、鸳鸯刀。
10. 武林大会和最终战。

### 阶段六：画面、声音和网页适配

只有核心行为通过测试后再做：

- 原版资源导入。
- 高清字体。
- 移动端布局。
- 战斗动画。
- 音乐音效。
- 触屏操作。
- 自动存档。
- PWA 离线运行。

否则美术会掩盖系统尚未复刻准确的问题。

## 十六、最小团队配置

高效配置是：

- 一名核心系统工程师：战斗、状态、存档、确定性。
- 一名前端游戏工程师：地图、渲染、输入、音频。
- 一名工具与数据工程师：导入器、编辑器、数据校验。
- 一至两名内容与 QA：任务录入、攻略核对、原版对照。
- 有公开发布需求时，再增加美术、音频和版权合作。

单人也能写出引擎，但完整内容录入和回归测试会成为真正瓶颈。

## 最终建议

这个项目不要叫“做一个类似金庸群侠传的网页游戏”，而应直接立项为：

《金庸群侠传 Web Classic Engine》：一个以原版行为兼容为目标的数据驱动武侠 RPG 引擎。

第一阶段只做一件事：

让玩家从自宅出发，按原版方式获得《连城诀》，并确保每一步都可以用旧攻略验证。

然后立刻做《笑傲江湖》全链路。一个验证最小闭环，一个验证最大复杂度。两者都准确后，再批量复刻剩余内容。这是风险最低，也最容易真正做到“极致复刻”的路线。
